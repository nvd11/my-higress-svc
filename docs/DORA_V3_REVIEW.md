## 2. 剩余问题（按严重度）

### 🔴 R-1（阻塞）门卫未声明请求体缓冲上限 → 会 413 掉真实流量

**问题**：门卫必须读取 JSON 请求体才能校验 `model`。`finops-audit` 中已有 `ctx.SetRequestBodyBufferLimit(50 * 1024 * 1024)`（`main.go:68`），但 v3 全文**未要求门卫设置同样的上限**。

**实测数据（近 7 天生产库）**

```
最大 prompt_tokens = 927,080   → 约 3.54 MB 请求体
prompt_tokens > 262,144（>1MB）的请求数 = 1,097 条
```

**后果**：若门卫沿用 Envoy 默认缓冲（MB 级以下），这 1,097 条长上下文请求会直接 **413 Payload Too Large**，且发生在门卫 `FAIL_CLOSED` 下 → 表现为大面积业务中断。

**修复建议**：门卫 `onHttpRequestHeaders` 中设置 `SetRequestBodyBufferLimit(50MB)`（与 finops 一致）；P1 用 **3.5MB 真实报文**做回归。

---

### 🔴 R-2（阻塞）`x-original-model` 的注入相位属未验证假设

**问题**：proxy-wasm 的通行限制是——请求头随 headers 阶段送出后，在 body 阶段通常无法再修改。而门卫必须**读完 body** 才能知道 `model`。

v3 将其写成既定事实（§1 收益第 4 条、§3.1 职责第 3 条），**未给任何备选方案**。

**三条备选（P1 择一验证）**

| 备选 | 做法 | 代价 |
|---|---|---|
| ① 顺序互换 | `finops-audit` 排在门卫之前（如 priority 950），先抓原始名；门卫后改写 | 需重验"门卫本地拒绝时，finops 是否仍收到回调" |
| ② 门卫自报事件 | 门卫自行发一条"准入决策"审计（含原始名 + `request_id`），后端按 `request_id` 与用量记录合并 | 后端需加合并逻辑（现有 md5 主键派生可复用） |
| ③ 反查表 | finops 用真名反查主名 | **丢信息**：无法区分用户用了哪个别名，G4 打折 |

**建议**：P0 阶段先用一个 5 行 demo 插件验证"body 阶段能否 `SetHttpRequestHeader`"；不可行则直接锁定备选 ②。

---

### 🟡 R-3（中等）被拒请求不落库 → 安全事件不可观测

**问题**：401/400 由门卫 `SendLocalReply` 本地返回，链路短路，排在后面的 `finops-audit` 很可能**收不到回调**。

**后果**：
- "谁在用错 Key 撞网关""谁在调未纳管模型"完全不可见
- v3 的 G1/G2 只验证响应正确性，**未验证是否留痕**

**修复建议**：新增 **G7**：`401/400` 事件必须可在账本或独立拒绝日志中检索到（含 `api_key_alias`、`model_requested`、`status_code`、时间）。

---

### 🟡 R-4（中等，事实错误）L2 的"<30 秒"不成立

**v3 原文**：*"修改 `config.yaml` 补充别名/主名，推送触发流水线热重载配置 · < 30 秒"*

**实测链路（2026-10-24 同日均实测）**

```
git push → CI 构建 wasm（~2 min）→ 推送 GHCR → GitOps 回写 bump 提交 → ArgoCD 同步 → 集群生效
合计 ≈ 3~4 分钟
```

`config.yaml` 的改动**不是热重载**，而是"重建镜像 + 重新部署"。

**修复建议**：L2 时效改为"**分钟级（3~5 min）**"；若确实需要 30 秒级，需另建"门卫名单以 ConfigMap 挂载 + 热更新"通道（独立改造，不在本方案范围）。

---

### 🟡 R-5（中等，安全债被固化）明文 A6 Key 被"保持"为长期方案

v1 的 P4 含"迁移 Secret 引用"；v3 的 R5 反而明确"**保持 Ingress 注解注入**"。这使明文密钥从"待办事项"变成"设计决策"。

**修复建议**：P4 补回一条"将 Ingress 注解中的 A6 Key 迁移至 K8s Secret 引用"，或明确记录"接受该风险"的决策人与日期。

---

### 🟡 R-6（中等，单一来源缺失）`virtual_keys` 将出现第二份副本

门卫需要校验 Key，但 v3 未定义 Key 存放位置。现状仅一份：`wasm-plugin.yaml:23`（**明文**）。

P3a~P3b 期间两份并存 → 密钥扩散面 +1，且必须人工保持同步。

**修复建议**：明确"Key 的唯一来源 + 过渡期同步规则 + 终态仅保留门卫一份"，并同时规划迁出明文。

---

### 🟢 R-7 三个小尾巴

| 项 | 问题 | 建议 |
|---|---|---|
| 模型级 `fallback:` | `config.yaml` 中该字段在路线乙下依然**不生效** | 删除该字段，或明确定义语义（需另做重试逻辑） |
| `model_used` 语义 | G4 只定义了 `model_requested` | 补：`model_used` = 门卫改写后的上游真名 |
| 定量承诺 | "≤150 行"、"< 0.05ms" 不可验证 | 改为 P1 实测指标：P99 增量延迟、门卫二进制体积、单测覆盖率 |
